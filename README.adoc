= IETF bibliographic data in Relaton format

This repository holds the combined IETF corpus — RFCs, Internet-Drafts and the
RFC sub-series (BCP, STD, FYI) — as Relaton v3 YAML, together with the
`Relaton::Index` manifests that resolve a reference to a file.

== What is here

`data/`:: One record per document, flat and lower-cased:
`data/rfc3986.yaml`, `data/std66.yaml`,
`data/draft-ietf-quic-transport-34.yaml`. An
Internet-Draft has a record per version plus an unversioned aggregator record.
+
The frozen mirror of legacy bibxml XML (`reference.*.xml`) that used to sit
alongside is removed by the first crawl: the run clears `data/` wholesale, and
the classic xml2rfc host it came from retired in 2024.

`index-v2.yaml` / `index-v2.zip`:: The document index. One row per record, keyed
by that record's primary docidentifier as a structured pubid hash:
+
[source,yaml]
----
- :id:
    _type: pubid:ietf:rfc
    number: '3986'
  :file: data/rfc3986.yaml
- :id:
    _type: pubid:ietf:std
    number: '66'
  :file: data/std66.yaml
----
+
Rows carry exactly `:id` and `:file` — `Relaton::Index` rejects an index with
any third key. `_type` is one of `pubid:ietf:{rfc,bcp,std,fyi,internet-draft}`;
a versioned draft also carries `version`. DOIs are not indexed: `10.17487/RFC3986`
is not a `pubid:ietf` identifier, and a single unparseable row invalidates the
whole file. DOI lookups are served by relaton's `doi` flavor.
+
A sub-series id resolves to its **own container record**, not to a constituent
RFC: 42 of the 365 sub-series include more than one RFC, so there is no single
document to alias to. `STD 66` returns `data/std66.yaml`, whose
`relation: includes` names the RFCs — one hop, and correct for all 365.

`index-v1.yaml` / `index-v1.zip`:: The same rows keyed by the primary
docidentifier as a plain string — the flat shape every relaton-data-* repo
publishes as `index-v1`:
+
[source,yaml]
----
- :id: RFC 3986
  :file: data/rfc3986.yaml
- :id: STD 66
  :file: data/std66.yaml
----
+
`crawler.rb` writes it from `data/` after the fetches. It needs no pubid, so it
still covers the corpus when pubid cannot parse an id.

== Where the data comes from

`crawler.rb` runs `Relaton::Ietf::DataFetcher` against the authoritative
sources. The records are v3 natively and `index-v2` is written by the fetcher
as the crawl runs, so there is no conversion step. The one thing built here is
`index-v1`, read back from the finished `data/`.

[cols="1,2,1"]
|===
| Source key | Origin | Produces

| `ietf-rfc-entries`
| `https://www.rfc-editor.org/rfc-index.xml` — `<rfc-entry>`
| `data/rfc*.yaml`

| `ietf-rfcsubseries`
| the same index — `<bcp-entry>`, `<fyi-entry>`, `<std-entry>`
| `data/bcp*`, `std*`, `fyi*`

| `ietf-internet-drafts`
| `rsync.ietf.org::bibxml-ids`, parsed from a local `bibxml-ids/`
| `data/draft-*.yaml`
|===

The drafts fetch reads `bibxml-ids/` off disk and does no fetching of its own,
so the crawler rsyncs the mirror first (anonymously; it is a public rsync
daemon module on port 873) and aborts if that fails — otherwise the fetch would
quietly produce no drafts at all.

Thin records — unversioned draft aggregators and BCP/STD/FYI groups, which have
no date, doctype or source of their own because the upstream sources publish
none — inherit them from their newest constituent inside the gem. A
`<bcp-entry>` in `rfc-index.xml` is a pointer and nothing more: a `<doc-id>` and
an `<is-also>`.

== Running the crawler

[source,sh]
----
bundle install
bundle exec ruby crawler.rb
bundle exec ruby crawler.rb --skip-rsync      # reuse an already-synced bibxml-ids/
bundle exec ruby crawler.rb --allow-shrink    # permit a smaller corpus than the committed one
----

Run it from the repository root: both the `bibxml-ids/` glob and the index file
are resolved relative to the working directory.

The crawl is **destructive by design**. `DataFetcher` only ever adds — it does
not remove records for documents withdrawn upstream, and `Relaton::Index`
accumulates on top of whatever index file it finds — so `data/` and any
`index*` are cleared first, making each run a snapshot rather than a union of
every run to date. A crawl yielding under 99% of the committed record count
aborts instead of publishing; `--allow-shrink` overrides that when the loss is
real. A crawl also aborts when either index has fewer rows than 99% of the
records it produced — `--allow-shrink` does not override that.

The `.zip` files are not written by the crawler: relaton/support's shared
`crawler.yml` zips any changed `index*.yaml` and commits both.

== Dependencies

`relaton` and `pubid` are both tracked from git `main`. `Pubid::Ietf` is in no
released pubid — the flavor and the fixes the index depends on postdate
`2.0.0.pre.alpha.9` — so the pin in `Gemfile` is required, not a convenience.
